# Milestone 3: Doctor Domain

The doctor domain is deployed as `dev-medislot-doctor-stack`. It attaches `/doctors/me` and its child paths to the REST API created by `dev-medislot-auth-stack`; it does not create another API. Protected routes use the existing JWT authorizer and accept only the `DOCTOR` role. Handler identity comes from `requestContext.authorizer.userId`, never from request data.

## Routes

| Method | Path | Purpose |
| --- | --- | --- |
| GET, PUT | `/doctors/me` | Read or update the professional profile, hospital details, and specializations |
| POST | `/doctors/me/photo` | Create a short-lived S3 upload URL for JPG, PNG, or WebP |
| GET, POST | `/doctors/me/consultation-types` | List or create a consultation type |
| PUT, DELETE | `/doctors/me/consultation-types/{id}` | Update or remove a consultation type |
| GET, PUT | `/doctors/me/availability` | Read or replace recurring weekly patterns |
| GET, POST | `/doctors/me/blackouts` | List blackouts or add one date/date range |
| DELETE | `/doctors/me/blackouts/{id}` | Remove a blackout |
| GET | `/doctors/me/schedule?date=YYYY-MM-DD` | Read a UTC-date schedule with confirmed patient bookings |

Consultation type durations and capacities follow the frozen rules. Types can be edited or deactivated; deactivation retains appointment history and prevents future slot materialization. A blackout request accepts `{"date":"YYYY-MM-DD"}` or inclusive `start_date` and `end_date`. Availability PUT replaces the doctor's complete weekly pattern set.

The dashboard displays the saved profile and offers an edit mode with persisted field values. Verification is set automatically after contact details, licence, experience, qualification, language, specialization, profile photo, and hospital name/city/address are present. Until then, consultation and availability writes are rejected by the API. Photo uploads are confirmed against the existing assets bucket before the profile key is saved and a signed viewing URL is returned.

## Slot Materialization

`SlotMaterializerFunction` runs daily at 02:00 UTC through EventBridge Scheduler. Availability and blackout dates use UTC throughout; there is no per-doctor timezone conversion. The rolling window is `/medislot/{environment}/booking-window-days` in SSM Parameter Store, initially 30 days. Slot start and end are stored as UTC timestamps. IDs are deterministic and remain ordinary slot attributes for SQL appointment correlation. The Slots table uses `doctor_id` as its partition key and `slot_start_time` as its sort key; materialized records also include `slot_end_time`, capacity, booked count, version, status, and consultation type ID. DynamoDB `attribute_not_exists(slot_start_time)` makes materializer reruns safe. Consultation names are read from RDS and are not stored in Slots.

The doctor day view and patient availability query the composite table key directly. Appointment `slot_id` remains a SQL reference to the ordinary slot attribute and is `BIGINT` so it can hold the deterministic DynamoDB slot identifier. The schema initializer removes the old doctor timezone column and checks the slot ID type idempotently.

## Appointment Booking

The patient stack exposes authenticated `POST /appointments/book` for `PATIENT` users. The JSON body contains `doctor_id` and the slot's UTC `slot_start_time`; patient identity always comes from the API authorizer. The request must include an `Idempotency-Key` header (8-255 non-space ASCII characters). The key is scoped to the authenticated user and bound to the canonical request body; reusing it for different booking data returns `409`.

The booking Lambda checks that the slot exists, is active, is in the future, and has room under its capacity. It uses a DynamoDB conditional update on `version`, `booked_count < capacity`, status, and slot time to reserve a seat, incrementing both `booked_count` and `version`. Conditional conflicts use retries of 50, 100, 200, 400, and 800 ms; exhausted conflicts and full slots return `409`. Capacity greater than one supports group/Health Camp slots.

MySQL is the appointment system of record. A transaction writes the appointment and its test payment record using the doctor's configured consultation fee. Clients may select `CREDIT_CARD`, `DEBIT_CARD`, `UPI`, `NET_BANKING`, `WALLET`, or `CASH`; each transaction gets a unique generated ID. The test-only `test_payment_outcome` may be `SUCCESS` (default) or `FAILED`. Failed attempts are recorded against a cancelled appointment, do not retain the reserved slot, and do not publish an appointment-booked event. Successful payments store `paid_at`; no real charge is made because there is no payment-provider integration. Cancellation creates a successful refund record and unique refund transaction ID for positive refund amounts, sets `refunded_at`, and changes the payment status to `REFUNDED`; zero-value refunds are marked `NOT_REQUIRED`. This is for application behavior and refund calculations only; no money moves. A patient-row lock serializes duplicate checks and the limit of five active appointments per patient. DynamoDB `${EnvironmentName}-idempotency-keys` caches the request response for 90 days and tracks whether its EventBridge event was published. No appointment-specific idempotency or outbox tables are created in RDS. Because the appointment and idempotency cache are in separate services, a failure after the MySQL commit but before the DynamoDB cache is written cannot provide a strict cross-database exactly-once guarantee. A failure before the SQL commit releases the DynamoDB slot reservation; if the commit outcome is uncertain, the seat is retained to avoid overbooking. CloudWatch metrics remain `SuccessfulBookings`, `FailedBookings`, and `BookingConflictRetries`.

The booking Lambda publishes `AppointmentBooked` directly to the default EventBridge bus with appointment identifiers, patient email/name, slot time, and `status=BOOKED`. EventBridge routes booking and cancellation events to the appointment notification Lambda, which sends email through SES and records delivery state in `${EnvironmentName}-appointment-email-notifications` to suppress duplicate deliveries. The sender is configured by `NotificationSenderEmail` in `parameters/patient-parameters.json`. Verify that sender identity in SES in the deployment region. While the SES account is in its sandbox, each recipient address must also be verified; request SES production access to email patients at arbitrary addresses. SES delivery failures are logged and EventBridge retries the target invocation. Booking event publication failures return an error and leave the idempotency cache marked pending for a retry. EventBridge delivery is at-least-once; consumers should deduplicate using appointment ID and event type.

Authenticated `GET /appointments` and `GET /appointments/{appointment_id}` expose appointment records. Patient queries are scoped to the patient profile for the authenticated user; doctor queries are scoped to that doctor's assigned appointments; `ADMIN` queries are unscoped. Listing accepts `limit` (1-100) and `offset` (0-100000). The schema supports `ADMIN` role values, but administrators must be provisioned through the trusted account-management path; public registration still only permits patients and doctors.

`POST /appointments/{id}/cancel` supports patient cancellation of their own booking and doctor cancellation of every active appointment assigned to that doctor's selected slot. `RefundService` reads refund thresholds and percentages from `/medislot/{environment}/REFUND_*` parameters. More than 48 hours receives 100%; exactly 48 hours receives 75%; more than 24 through exactly 48 hours receives 75%; exactly 24 through 6 hours receives 50%; less than 6 hours receives 0%. Doctor cancellations always receive the configured doctor-cancellation percentage, regardless of timing. A doctor can mark an appointment as a no-show after its start with `POST /appointments/{id}/no-show`; this records a 0% refund and 100% deduction. The `refunds` table stores refund amount, deduction amount, and percentage, and `GET /patients/refunds` returns these values for the authenticated patient. Refunds are ledger records only; no money moves.

Cancellation and refund rows commit in MySQL. Patient refunds are calculated from the stored simulated payment amount and the configured cancellation windows; doctor cancellations always record a full refund. Refund rows record the amount and policy result only. Afterward the cancellation Lambda uses a DynamoDB transaction to insert a unique seat-release marker and decrement `booked_count` while incrementing `version`, then publishes `AppointmentCancelled` and `SlotSeatFreed` directly. The appointment notification Lambda emails the affected patient with the cancellation and recorded refund details. The marker prevents a retry from decrementing twice. `CancellationsByTier` is emitted with the `Tier` dimension. EventBridge is at-least-once; consumers must deduplicate by appointment ID and event type. This deployment has no payment processor integration, so no money is charged or transferred.

Appointment test files were removed by request, so automated appointment tests are not currently run in CI. See [appointment-concurrency-design.md](./appointment-concurrency-design.md) for the optimistic-locking rationale and retry semantics.

The patient availability page submits booking requests through the Flask portal, which forwards them to the authenticated API and shows the booking result. Past slots are filtered from patient availability using UTC and rechecked when a booking form is submitted; the booking API also independently rejects past slots. The `SlotsTable` resource is recreated as `${EnvironmentName}-slots-v2` with the composite key; existing slot records are not migrated. Run the slot materializer once after deployment to populate the new table rather than waiting for its next daily 02:00 UTC schedule.

## Deployment

The workflow deploys network, data, IAM, and auth first, then uploads `web/doctor-portal` to the assets bucket exported by the data stack and deploys the doctor stack. It creates a new deployment for the existing API stage after adding the doctor resources. IAM roles and the EC2 instance profile are defined in the IAM stack; the HTTP security group is defined in the network stack. The doctor portal EC2 instance is in the existing public subnet; RDS remains private. Set `PortalAccessCidr` in the network parameters to the intended source range.

The portal opens on a doctor registration-first welcome page, then supports sign-in, profile and consultation editing, availability editing, UTC day schedule viewing, and photo upload to the existing assets bucket. Access and refresh tokens are held in Flask's server-side filesystem session under `/var/lib/medislot/sessions` so they survive temporary-directory cleanup and portal restarts on the instance. The portal uses the platform API and has no database credentials.
